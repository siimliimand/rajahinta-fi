# Project Guardrails

> Auto-generated by `/make-guardrails`. Regenerate with the same command when architecture or conventions change.

## Architecture Constraints

- **Modular monolith for MVP.** The application is planned as a modular monolith with five layers: Data Acquisition, Core Domain, Data Platform, Application/API, Presentation. No code may cross these planned boundaries without an explicit decision to extract a module.
- **Calculator, not a shop.** No checkout, no payment collection for alcohol, no order management for physical goods. The only commercial transaction is the software subscription.
- **Neutrality enforced in code.** Ranking and sorting logic must be objective and deterministic. There must be no code path allowing a paid or manual boost to a merchant's position.
- **Tax/rate data is versioned, never overwritten.** Historical rates must remain queryable after a rate change; past calculations must resolve against the rate version effective on the relevant date.
- **Data freshness is a first-class citizen.** Every externally sourced fact (price, shipping cost, tax rate) carries a reliability status and timestamp surfaced to the user.
- **Minimal personal data.** Default to anonymous usage. Identity and age-verification data, if legally required, are a separate isolated subsystem.
- **Transaction Classification is isolated.** The most important proprietary logic is an independently testable module with versioned rule sets. Outputs are observed patterns with confidence and evidence, never bare legal conclusions.
- **Disclaimer is structural.** The "estimated total cost in Finland, not final legal tax liability" disclaimer must be a structural part of every result object, not a UI-only string.
- **Background jobs off the request path.** Price ingestion, transport-rate refresh, tax-dataset review, and time-series aggregation run as scheduled/queued jobs separate from the user-facing request/response path.

## File Organization

- No application source code exists yet (greenfield). When added, split files by domain/feature (e.g., `excise-engine.ts`, `container-duty.ts`, `transaction-classifier.ts`) rather than catch-all files like `utils.ts` or `constants.ts`.
- A file that imports from 5+ unrelated modules is a sign it should be split.

## Domain-Specific Rules

- **Excise and container-duty are separate sub-engines.** They are independently versioned, with different rules and exemptions. Container duty must check deposit-return system exemption before applying the general rate.
- **Unknown deposit status = ESTIMATED.** If deposit-system status cannot be determined, the container-duty calculation must be explicitly flagged as ESTIMATED, never silently assumed either way.
- **Rates are never auto-published.** A recurring job checks for newly published official rate changes and creates a task for manual/legal confirmation before any new dataset version goes live.
- **Feature flags for compliance-sensitive changes.** New merchant sources, new tax rulesets, and new UI ranking behavior must be gated behind feature flags for instant rollback.
- **Every number is explainable.** Every calculated figure (excise, container duty, transport, total) must be traceable to the exact input values, rate dataset version, and timestamp that produced it.
