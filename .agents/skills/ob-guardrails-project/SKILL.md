# Project Guardrails

> Auto-generated by `/make-guardrails`. Regenerate with the same command when architecture or conventions change.

## Architecture Constraints

- **Modular monolith for MVP.** The application is planned as a modular monolith with five layers: Data Acquisition, Core Domain, Data Platform, Application/API, Presentation. No code may cross these planned boundaries without an explicit decision to extract a module.
- **Calculator, not a shop.** No checkout, no payment collection for alcohol, no order management for physical goods. The only commercial transaction is the software subscription.
- **Neutrality enforced in code.** Ranking and sorting logic must be objective and deterministic. There must be no code path allowing a paid or manual boost to a merchant's position.
- **Tax/rate data is versioned, never overwritten.** Historical rates must remain queryable after a rate change; past calculations must resolve against the rate version effective on the relevant date.
- **Data freshness is a first-class citizen.** Every externally sourced fact (price, shipping cost, tax rate) carries a reliability status and timestamp surfaced to the user.
- **Minimal personal data.** Default to anonymous usage. Identity and age-verification data, if legally required, are a separate isolated subsystem.
- **Transaction Classification is isolated.** The most important proprietary logic is an independently testable module with versioned rule sets. Outputs are observed patterns with confidence and evidence, never bare legal conclusions.
- **Disclaimer is structural.** The "estimated total cost in Finland, not final legal tax liability" disclaimer must be a structural part of every result object, not a UI-only string.
- **Background jobs off the request path.** Price ingestion, transport-rate refresh, tax-dataset review, and time-series aggregation run as scheduled/queued jobs separate from the user-facing request/response path.

- **Unit volume is canonical litres, one convention.** `product_master.unit_volume` stores per-unit beverage volume in litres (feed millilitres ÷ 1000 at mapping, seeded litres, backfilled once 2026-09-26) and MUST satisfy `0 < unit_volume < 100`. No write or read path may reinterpret it as millilitres; the ingestion quality stage flags out-of-window rows, and the D1 port degrades reads ≥ 100 L to ESTIMATED with a metric rather than converting.
- **The calculator sanity rail never changes amounts.** When a line's excise exceeds 5× its retail price, the rail may only lower confidence/statuses (LOW / ESTIMATED) and add `sanityNotes`; every monetary figure stays byte-identical. Golden fixtures stay rail-free.

## File Organization

- Application source code is split by domain/feature (e.g., `excise-engine.ts`, `savings/gap.ts`, `price-context/window-stats.ts`) rather than catch-all files like `utils.ts` or `constants.ts`.
- A file that imports from 5+ unrelated modules is a sign it should be split.

## Domain-Specific Rules

- **Excise and container-duty are separate sub-engines.** They are independently versioned, with different rules and exemptions. Container duty must check deposit-return system exemption before applying the general rate.
- **Unknown deposit status = ESTIMATED.** If deposit-system status cannot be determined, the container-duty calculation must be explicitly flagged as ESTIMATED, never silently assumed either way.
- **Rates are never auto-published.** A recurring job checks for newly published official rate changes and creates a task for manual/legal confirmation before any new dataset version goes live.
- **No feature flags.** The flag and launch-gate systems were removed (2026-09-07, owner decision): every feature ships unconditionally enabled, and no `FF_*`/`LAUNCH_GATE_*` env var may gate behavior. Rollback is `wrangler rollback`, not a flag flip. Do not reintroduce flag-gating without an explicit owner decision.
- **Crawlable soft gate.** The age gate never removes content from server HTML: `RootLayout` reads `age_confirmed` server-side, `AgeGate` renders `{children}` unconditionally, and unconfirmed visitors get a modal overlay. The API boundary is the enforcement point (gated endpoints keep their 403s). Do not reintroduce an SSR placeholder or content-replacement gate.
- **Every number is explainable.** Every calculated figure (excise, container duty, transport, import VAT, total) must be traceable to the exact input values, rate dataset version, and timestamp that produced it.
- **Import VAT is foreign-seller-only and domestically absent.** The import-VAT line applies only when the seller country differs from the destination, using the same seller/buyer signal transaction classification consumes; domestic results carry no VAT surface anywhere (absence, not a displayed zero), pinned byte-identical to the pre-VAT engine. The VAT base composition is part of the versioned dataset, never inline code.
- **Insight surfaces are display-only and factual.** Savings snapshots, price-context figures, allowance citations, and guides never feed calculator, ranking, or basket inputs (compliance tests pin byte-identity), and the content lint bans advice phrasing ("best deal", "good time to buy", "buy now") on all public surfaces.
- **Finnish copy is glossary-governed.** UI copy in `src/messages/{fi,en}.json` carries one canonical term per concept per `docs/fi-copy-glossary.md` (`juomatarve`, `Ostoskorilaskuri`, `tullivapaat määrät`, `etanolin grammahinta` rendered in `snt/g`, `halvin ensin`); introducing or renaming a term updates the glossary in the same change. FI consumer surfaces use native register — no engineering calques (`deterministinen`, `rajattu syöte`); EN methodology copy deliberately keeps spec register. The ethanol unit price renders the computed `centsPerGram` verbatim — no display conversion exists.
- **Client analytics are observability outputs only.** Faro RUM is env-gated (no-op when `NEXT_PUBLIC_FARO_URL` is unset), identity-free and session-scoped (no user IDs, account data, or form contents; repeat usage cohort-level only); funnel events are a closed set (`calc_started | calc_result_seen | basket_optimized | alert_set`) emitted at flow success points, and no analytics signal is ever an input to calculations, ranking, or ordering.
- **Out-of-stock offers never become defaults.** Calculator `selectBestOffer` and allowance-fill candidate picking skip persisted `out_of_stock` offers; if every offer is out-of-stock, fall back to current behavior rather than failing (offers stay in responses for price-history context). Benchmarks, stock badges, and Etämyynti/Etäosto badges are additive display fields pinned byte-identity by compliance tests.
- **The basket guard bounds the whole optimization.** `MAX_TOTAL_COMBINATIONS` must bound the DFS and any per-merchant shipping work — compute shipping lazily (memoized per merchant-subset inside the search), never pre-enumerate powersets outside the guard; item-cap breaches stay a 400 ValidationError, 422 is reserved for the combinations guard.
- **Alert kinds are a closed, kind-guarded set.** `PRICE | TAX_CHANGE | LANDED_COST | CATEGORY` in the same `price_alerts` table; each active row is evaluated exactly once by its own branch, foreign kinds skipped before any read or counter (skip paths emit no evaluation count). LANDED_COST emails cite the close's provenance-observation composition from stored records — never recomputed; an unretrievable composition means skip, never a partial email. The CATEGORY sweep is deterministic: minimum fresh product-wide `priceCloseCents`, lowest-`productId` tie-break, bounded by the product category index.
- **Breakdowns are count-only below the floor and display-only everywhere.** Accuracy breakdown cells under 10 outcomes expose no share (a distinct count-only state, share forced null server-side); the breakdown read path never feeds calculator, ranking, or basket inputs (compliance-pinned byte-identity).
- **Transport quotes are only as honest as their joins.** The carrier resolves from `merchant_registry.carrier_id` (NULL = UNAVAILABLE, never a guess); shipping tier derives from total shipment weight against the carrier's own bracket ceilings (containerType is not a transport input); lookup weight is per-unit × quantity; transport VERIFIED requires an exact bracket on a stored product weight (volume-estimate basis caps at ESTIMATED). Curated carrier datasets (fransberg, posti, omniva, pakettipojat, norrlog) are append-only, governance-gated, and synced by the monthly cron — the gate MUST read the durable D1 store, never the empty in-memory default.
- **Seed writes are natural-key upserts; quota windows are sized to first-run cost.** The D1 seed's merchant-registry section upserts on UNIQUE(`merchant_id`) with no explicit id — an operator-added registry row must never PK-swallow a bootstrap row. The ingestion workflow's chunk-budget window must place a durable-sleep boundary before the per-invocation D1 quota dies for the worst-case (FIRST-run) per-pair cost of any mid-size catalog — re-run profiles are ~4× cheaper per pair and mask the hazard. A production quota-tail (the 1 s sleep does not reliably reset the quota window there) is healed by a fresh-instance re-run; the scheduled daily pass is always a fresh instance.
- **Offer VERIFIED is operator-only.** Ingestion pins every new offer ESTIMATED; the only VERIFIED writer is the audited ops verify action (attributed, bearer fail-closed), and verified offers age to STALE through the same freshness window as everything else.
- **Watermark reads are job-scoped.** `aggregation_watermarks` is a generic keyed table whose rows carry job-specific semantics (ISO instants for time-series aggregation, numeric product-id cursors for the savings pass): every reader MUST select its own job's row (`WHERE job_name = …`), never a table-wide aggregate over the watermark column — lexicographic TEXT ordering silently breaks across semantics (the "9194"/"0" shadowing incidents, 2026-10). Display boundaries shape-check watermark values as ISO-8601 before `Date.parse` (unparseable renders absent, never a fabricated date).
- **One listing universe, one predicate.** `PRODUCT_LISTING_UNIVERSE_SQL` (alcohol category ⇒ `alcohol_by_volume > 0` AND `review_hold_reason` IS NULL) is the single definition of what a product surface may list; every additional filter (category, search, sort) conjoins with AND onto it — never append a second WHERE onto the fragment's base (the post-merge `listCatalogKeys` 500). The ingestion guard holds zero-ABV and unparseable-ABV rows out of alcohol categories (`NONALCOHOLIC_HOLD_REASON = 'nonalcoholic_in_alcohol_category'`); hold-for-review never delete; the ESTIMATED-status contract for unparseable fields is untouched. Cleanup of pre-existing rows goes through the audited dry-run-first `scripts/nonalcoholic-catalog-audit.ts`, never a migration.
